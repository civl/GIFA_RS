# 视觉识别：骨架（M8a 的先行版）

更新时间：2026-11-22。**这不是 M8 的交付**，是把"截帧 → 采样 → 出角度 → 叠加层"这条链路
先接通的骨架。真正的算法移植（M8b）仍然没做，黄金帧基线也还没有。

## 链路

```
采样窗（屏幕坐标）
      │  GDI BitBlt，只截这一小块
      ▼
   Frame(RGBA)  ──▶ detect_simple  ──▶ VisionEvent ──▶ overlay_update
   216×216 典型        占位算法            带耗时          红箭头 + 绿弧
```

采样窗由 UI 线程每帧算好放进 `Arc<Mutex<Option<SampleBox>>>`，识别线程自己取 ——
窗口移动、切布局、换分辨率都不需要重启线程。

## 为什么先用 GDI 而不是 DXGI

DXGI Desktop Duplication 是二期该走的路（性能、独占全屏），但它的 COM 生命周期、
桌面复制会话重建、全屏切换都要专门处理。骨架阶段的目标是"能拿到一帧"，
把 COM 调试和链路验证混在一起只会两边都慢。

GDI 走 DWM 合成后的桌面：窗口化/无边框游戏拿得到；**独占全屏会返回黑帧**——
那本来就要求用户改窗口化（见 `IMMERSION.md`）。

## 箭头通道：已按原版移植并对拍通过 ✅

`crates/gifa-vision/src/arrow.rs` 是对 `webview-preload.js:566-960` 的**逐步骤移植**：

```
自适应阈值(p99≥100, floor 112, ×0.74) → 半径带 mask → 连通块(取最大)
→ 72 格径向剖面 → 三点平滑 → 候选峰(≥50% 峰高、间隔≥25°) + 支撑宽度
→ 峰值精修(平均单位向量) → 枚举三点组合打分 → 定鼻尖
→ 角度 = 两尾翼中分线反向；validity 七道闸
```

**对拍结果：33 帧合成语料（箭头 + 视锥两条通道），Rust 与 JS 参考实现逐帧一致**
（最大角度差 0.0000°，最大 conf 差 1.11e-16；valid / cyans / tipFrac / angMargin /
radMargin / noseFlat 全部相等）。

### 对拍是怎么做的

`tools/vision-ref/harness.js` 在运行时**从原版源码里切出算法段**（不抄、不重写），
在 node 里跑；同一批 `.bin` 帧再喂给 Rust：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/vision-golden.ps1
```

合成帧生成器画的是"钝鼻 + 两个尖尾"的飞镖：鼻子半径 0.17、尾翼 0.235、
翼角 ±130°（两尾翼夹角 100°）。这些比例是按原版注释里的实测值（tails 100°、
nose→tail 123~137°、nose 半径最小）反推的 —— 画成实心三角会直接判无效。

### 移植时踩的四个坑

1. **角度空间**：原版给的是 `atan2` 角（0=东、逆时针），叠加层要罗盘角。
   换算是 `compass = (90 − atan2) mod 360`，**不是** `+90` —— 写成 `+90` 会让所有方向镜像。
2. **诊断字段是舍入过的**：原版返回 `Math.round(x*100)/100`，而 Rust 的 `round()`
   在 .5 上朝远离零舍入，JS 是 `floor(x+0.5)`，差 0.01。
3. **阈值比较要用 double**：`score < thr` 里 thr 是小数，我第一版截断成整数，
   卡在阈值上的像素会多算进来。
4. **f32 缓冲的取整位置**：JS 用 double 算完再存进 `Float32Array`（只取整一次），
   Rust 若全程 f32 运算会提前取整，边界像素归属分歧。

## 视锥通道：已按原版移植并对拍通过 ✅

`crates/gifa-vision/src/cone.rs` 移植 `analyzeCone()`（`webview-preload.js:1008-1358`）：

```
极坐标格(120×12) → 不透明白核剔除 + 膨胀 → 每格 RGB 累加
→ 逐角度找「半径边」：两侧各 2 格取均值，三通道联合最小二乘解 α，
  且要求三通道解出同一个 α（水→陆这种底色边界残差超标，判 0 并投反对票）
→ 可见层严格多数（≥5 层）才算一条边
→ 配对：上升边 −45°、下降边 +45°（张角恒 90°），单边也允许
→ 亚格细化（±2 格强度质心）→ 中轴 → 角度
```

它认的是**半透明白膜** `dst = src + α·(255−src)`，α 随半径衰减（0.17R≈0.35 → 0.72R≈0.12）。
合成语料必须按这个混色画，画成实心白会解出 α≈1，被 `A_MAX=0.45` 直接否掉。

**对拍同样 33 帧全一致**：视锥最大角度差 0.0000°。
`--vision-synth` 端到端：视锥 **178.5°**（期望 180°，差的 1.5° 是算法自己的量化步长，
和原版一模一样）。

## 箭头的几何定义（用户给的标准，2026-11-22）

> 行进方向（红箭头）是角色的**面朝方向**，在小地图中以**天青色四边形**标识。
> 四边形中有 3 个点的那条边是**底边**（中间那个点是凹口），
> 这 3 个点朝余下那个点"射"出的线，交叉处就是行进方向。

换成算法语言：

```
        T（尖端，剩下那个点）
       / \
      /   \          方向 = 底边中点 → T
    W1  N  W2          N = 3 点边的中间点（凹口）
      \ | /
       底边
```

* **4 个角**：尖端 T、两翼 W1/W2、凹口 N；
* 底边上 3 个点 = W1、N、W2（N 在中间）；
* 方向 = 从 N 指向 T。

实测两枚真机箭头都符合：尖端半径最小（12.6 / 13.6px）、凹口最钝
（支撑宽度 21~23 格，两翼只有 3~4 格）。

补充（用户 2026-11-22 第二次说明）：底部其实有 **3 个外凸点**（两翼 + 底边中点）
和 **2 个向内凹点**，加上尖端一共 **6 个顶点** —— 是个六边形，不是三角形。

**这两个凹点是唯一的结构**：三点拟合要在四个角里猜"哪个是鼻子"，翼角一偏方向就整段歪；
而凹点一定在背后，冒充不了。所以 `crates/gifa-vision/src/hexagon.rs` 用它当兜底：

```
两个凹点 → 中点 M 是"背后" → 离 M 最远的边界点就是尖端 T → 方向 = M → T
```

180° 歧义从定义上就不存在，不需要翻转判据。

**这也解释了 v1 为什么能工作**：原版"取半径最小的角当鼻子、方向取两翼中分线的反向"，
本质就是在用同一个几何 —— 只是它用两个翼角去反推，翼角一歪方向就歪；
而按上面的定义，可以直接用 N→T 定方向，翼角只用来验证对称性。

### 形状模型重做：v2 凸包 + 凹口（`crates/gifa-vision/src/template.rs`）

先说结论：**"改形状模型"这条路，单靠改形状分不出方向**。

真机箭头近似等边（尖端 17.5 / 两翼 16.6·16.7 / 底边 12.6），三个顶点谁当尖、谁当翼，
光看形状没有信息量。实测把"参数化四边形 + IoU 拟合"跑上去，三种顶点分派 IoU 几乎一样高，
角度在 211° / 334° / 107° 之间乱跳 —— 不是调参能救的，是**问题本身欠定**。

真正能把方向钉死的只有一样东西：**凹口**。底边中点比两翼更靠近中心（12.6 < 16.6），
整块掩膜唯一的内凹点就在"背后"。所以 v2 的做法是：

```
最大青色连通块 → 边界点 → 凸包 → 离凸包最远的边界点 = 凹口
             → 方向 = 质心的反方向 → 对称轴 ±25° 精修
```

凹口深度 < 0.03·R 时直接返回 None（纯凸形状没有方向信息，宁可不报）。

v2 单独用的精度不如 v1（净图 99.8° vs 真值 89.0°，v1 是 90.2°），
但它的**错误方向和 v1 不一样** —— 这正是它的用处。

### 试过但**不成立**的两条：帧间位移、视锥互证

**1. 帧间位移方向（相位相关）——信号太弱**

设想：小地图随角色移动而滚动，相邻帧做相位相关就能拿到位移方向，
作为"箭头认不出时"的补充观测。实测（蒙德素材，1400×788 沉浸，约 10 fps）：

| 基线 | 位移中位 | 相关峰值中位 | 方向一致性 |
|---|---|---|---|
| 1 帧 | 0 px | 0.91 | — |
| 5 帧 | 1 px | 0.38 | 27% |
| 10 帧 | 0~1 px | 0.32 | 45% |

三层原因，每一层都足以否掉这个方案：

* **尺度**：小地图约 100 m 铺 250 px → 0.4 px/m；角色 5 m/s → **2 px/s → 0.2 px/帧**，
  远低于可测精度；
* **静态件锚定**：外圈装饰和「北东南西」方位字不随地图移动，会把相关峰钉在 (0,0)；
  只取中心区域后峰值掉到 0.3~0.4，方向变成随机；
* **旋转**：这张小地图会随镜头旋转，纯平移的相位相关建模不了。

**2. 视锥互证——前提本身就是错的**

原以为"跑动时箭头（行进）与视锥（镜头）基本一致"，实测 55 帧里夹角中位 5.2°、p90 11.9°，
看起来可用。但接入后 290 帧里**误挡 16 帧**：

* 原神的移动是**镜头相对**的 —— 按 A/D 横移时箭头与镜头朝向**垂直**；
* 按 S 倒着走时两者差 **180°**。

放宽成"共线即可（0° 或 180°）"仍会挡掉横移帧。结论：这条不变量不存在，已撤除。

### 我们加的闸：鼻子必须在轴上

真箭头是轴对称图形，鼻子必然落在中轴上。实测这个量能把两类情况分开：

| 素材 | &#124;鼻子−轴&#124; | 角数 |
|---|---|---|
| 合成飞镖 ×30 帧 | 最大 **2.5°** | 3 |
| 真机干净箭头 | **6.5°** | 4 |
| 真机箭头+地图背景 | **13.9°** | 5 |

`arrow::axis_consistent()` 用 8° 卡这条线：挡住被污染的那一帧（它恰好就是偏 11° 的那帧），
不误杀前两类。**这是我们的增补，不在原版里**，所以 `analyze()` 的输出仍与原版逐位一致
（黄金对拍 33 帧 0.0000°），闸门只加在管线入口。

真实像素回归：`crates/gifa-vision/tests/real_arrow.rs` 用这两枚真机箭头钉住行为
（cyans 331 / 角数 4 与 5 / 角度 90.2 与 101.8，均与原版 JS 一致）。

## 自动定心（--autocenter）现在能用了

流程：

```

```

实测（蒙德视频，1400×788 沉浸）：

```

第 2 次一致 → cx=0.1495 cy=0.2468
采用半径 0.14375（最近内置预设差 0.0026）
```

也就是说**内置「你的影月月」(0.1469, 0.2463) 本来就是对的** ——
之前几轮视频里箭头 0%，是我自己用 `--roi 0.086,...` 把采样窗带偏了，不是内置预设的问题。

半径的三次尝试都失败了，记在这里免得再犯：

| 做法 | 结果 |
|---|---|
| 沿用当前布局的 r | r=0.18 时窗口 311px → 14% |
| 按 `窗口 = 箭头×12` 反推 r | 得到 0.20（夹到上限），0% |
| **取最近内置预设的 r** | **0.14375（窗口 250px），标注语料上 96%** |

原因：r 同时受"小地图缩放"和"显示器宽度"影响，单看箭头反推必然跑偏。

## 重试策略（recovery）与"页面侧不留识别"

### 重试策略

移植 `analyzeArrowWithRecovery` / `analyzeConeWithRecovery`（`webview-preload.js:1569-1614`）：

```
主判据失败 → 窗口往里缩 2.5% → 8 个方向各偏移一次 → 每个跑一遍检测
          → 按角度聚簇（±12°）→ 只有"≥3 票且过半"的簇才采纳，角度取簇内均值、conf 封顶 0.68
```

单次重试容易被噪声带偏，**簇投票**才是重点：孤立的伪峰凑不出 3 票。

约束都照原版搬：`conf ≥0.5`、`tipFrac ≤0.28`、质心离窗口中心 ≤0.1×边长、面积 ≤10%。
视锥那支要求 `size ≥ 380` 才重试 —— 我们的采样窗 126~311，所以它实际上不会触发（与原版一致）。

回归：`recovery_does_not_lose_frames` —— 主判据已经有效的帧，重试**不许**把它改判成无效。

### 页面侧不留识别

原版是在 preload 里跑 `tickBearing` 的。我们改成 Rust 之后必须确认没把那段 JS 带进来，
否则两套并行：白烧一份 CPU，两边结果还会打架。

现状：注入页面的只有两个脚本 —— `crates/gifa-player/assets/player-agent.js`（播放器控制）和 `crates/gifa-shell/assets/overlay.html`
（叠加层动画，里面的 rAF 只做补间）。两个都不含视觉代码。

`--check` 新增一行把这件事钉住：

```
[1] 页面侧没有识别循环   PASS  注入的两个脚本里都没有 tickBearing/analyzeCone
```

它直接对 `include_str!` 进来的源码做子串检查 —— 以后谁把原版 preload 粘进来，这一行立刻变红。

## 占位检测器做了什么

只做两件事，够验证链路：

1. **箭头**：采样窗中心圆盘带内（`RADIUS_MIN..MAX`）的青色像素（`cyan_score ≥ 112`）
   质心方向 → 罗盘角。
2. **视角**：近白像素（`min(r,g,b) > 200` 且 `max-min < 28`）质心方向。

**小地图存在性门控**照抄了原版：`cyan_frac < 0.0015` 就直接返回空——
没有小地图的帧（转场、对话、看视频）不能靠白像素硬凑一个视角出来。

⚠️ 明确不做的：自适应阈值（p99）、最大连通块、72 格径向剖面、三点枚举评分、极坐标格、
最小二乘白膜边、α-β 滤波、大跳门限、扇形投票。这些必须逐函数对照
`webview-preload.js:365-2050` 移植，凭理解先写一版会把对拍基线搞乱。

## 这轮修掉的 bug

修法：**先拷贝像素，再清理 GDI 对象**。

## 兜底通道 v3：主轴 + 两端宽度（2026-11-23）

用户提的几何模型：小地图是圆，箭头（六边形）绕圆心转、半径固定，所以

1. **只看 1.2×箭头半径的内圆** —— 省算力，也天然排除圆外的干扰青色
2. 底座 5 点 4 边，两点连成 L1、两内点连成 L2，**L1 ∥ L2 ⟂ L3**，L3 = P0→鼻尖
3. 方向 = P0 → 鼻尖

按这个模型实现了一版（枚举"带凹口的平边"当底边，用它和鼻尖的中轴做垂直校验）。
**结论：模型对，但"底边"这一步在真机上不唯一** —— 小地图里箭头常被地形青切掉一角，
形状接近三角形，而三角形的**每条边**都能凑出垂线，于是会选到侧翼边（实测整体偏 ~120°）。

真正稳的性质是模型里没明说但隐含的那条：**箭头关于中轴严格对称**。落地成 v3：

```
1. 取内圆里的最大青块，对像素做 PCA → 主轴方向（±180° 不确定）
2. 沿主轴两端各取 20% 长度，量垂直方向宽度
3. 窄的那头是鼻尖 → 定符号 → 罗盘角
```

### 实测（两份人工真值语料）

| 算法 | 真机 39 帧 | 视频 138 帧 |
|---|---|---|
| v1 三点拟合 | 28/39，中位 9.3°，翻转 0 | 138/138，中位 0.0°，翻转 0 |
| 六边形 v1（凹口中点→最远点） | 39/39，中位 4.8°，**翻转 2** | 138/138，中位 4.8°，**翻转 59** |
| **v3（主轴+宽度）** | 39/39，中位 **2.4°**，**翻转 0** | 138/138，中位 4.0°，**翻转 0** |
| 管线（v1 优先 + v3 兜底） | 39/39，中位 9.0°，**翻转 0** | 138/138，中位 **0.0°**，翻转 0 |

"翻转"= 误差 > 45°。

v3 在**两份语料上都是零翻转**，中位精度也比原六边形好。管线已切到 v3，
并加了两条回归测试（样例箭头朝北、真机语料零翻转）。

复现：

```
cargo run -p gifa-vision --example corpus-eval
```

### 关于"只看内圆"的省算力

`direction_v3(rgba, size, center, r_arrow)` 支持传箭头半径：传了就把 mask 限制在
1.2×r 的内圆里；传 0 就自己量（取最大青块到圆心的最远距离）。

注意：**省的是兜底这一步的算力**，而管线的大头在截帧和 v1——所以这条优化对
整体帧率影响很小（v3 本身在 126px 窗口上 <0.3ms）。真正省算力要动截帧（DXGI）。


## 模板匹配 / NMS / 旋转不变性：三个提法的实测结论（2026-11-23）

### 1. 多角度模板库 + NMS

做法：把语料每帧的青色 mask 按**真值角度反向旋转**到统一朝向，平均成一张模板；
匹配时逐角度旋转模板做归一化互相关（NCC），多峰之间按 ±15° 做 NMS。

**留一交叉验证**（模板从其余帧训练，避免"自己测自己"）：

| 算法 | 真机 39 帧 | 视频 138 帧 |
|---|---|---|
| 模板匹配 + NMS（10° 步长） | 39/39，中位 **1.3°**，最大 11.7°，翻转 0 | 138/138，中位 **3.5°**，最大 5.9°，翻转 0 |
| v3（主轴+宽度） | 39/39，中位 2.4°，最大 9.7° | 138/138，中位 4.0°，最大 16.2° |
| v1 三点 | 28/39，中位 9.3° | 138/138，中位 0.0° |

同域内模板确实更准一点点（+1°），但**跨域完全不能用**：

| 训练 → 测试 | 中位 | 最大 | 翻转 |
|---|---|---|---|
| 真机 → 视频（缩放到 96×96） | 13.7° | 113.7° | 9 |
| 视频 → 真机 | 20.6° | 126.6° | 11 |

模板学到的是**这一种渲染外形**（分辨率、缩放、抗锯齿、背景混色都不一样）。
结论：除非按"每张地图 / 每种分辨率"各带一份模板（脆弱，而且换 HUD 缩放就废），
否则不值得为 +1° 引入模板库。真要用，正确做法是**在设备上自举**（拿高置信帧现学），
而不是随包发模板。

### 2. NMS 到底有没有用

NCC 的峰值地形**是单峰的**：177 帧里，"次峰"与"主峰"的角度差全部 < 30°。
也就是说 NMS **一次都没触发过** —— 方向搜索空间里根本不存在"重复的低质量匹配"。

NMS 真正该用的地方是**空间上的多候选检测**（一张图上多个框/多个同类目标）。
我们的管线是"最大连通块 + 单峰"，天然没有这个问题。

### 3. 旋转不变性：已经有了，而且能测

`examples/rotation-sweep` 把真机帧绕中心转一圈再测：

| 算法 | 0°/90°/180°/270° | 其余朝向 | 合计 |
|---|---|---|---|
| v1 三点 | **直接失效** | 8.5°~11.4° | 可用 17/36 次，中位 8.6° |
| v3 主轴 | 3.7° | 3.7°~4.1° | 可用 36/36 次，中位 **3.7°** |

v3 是**旋转等变**的（每个朝向误差几乎相同），v1 既不是等变、还会在四个正朝向上失效。
这也解释了为什么 v3 兜底的效果那么好。

### 4. 顺带证否了一个假设

真机帧里箭头质心离采样窗中心 **6.09px**（箭头半径才 ~13px），看着很像
"v1 以窗心为原点"导致的偏置。于是实现了"先用质心把图平移再跑一遍"：

| | 真机 | 视频 |
|---|---|---|
| v1 原样 | 9.3° | 0.0°（p90 0.5°） |
| v1 居中重跑 | 9.3°（无变化） | 0.0°（p90 2.0°，**变差**） |

**假设证否**，代码已撤掉。v1 那 9° 是三点拟合在这种外观下的固有偏差，不是居中问题。

### 5. 真正卡住我们的是语料，不是算法

真机 39 帧的真值分布：

```
315°~360°  28 帧      ← 绝大多数
  0°~ 45°   5 帧
 45°~ 90°   6 帧
 90°~315°   0 帧      ← 完全没有
```

而 v1 有效的 28 帧**全部**落在 315°~360°。也就是说：
**任何"v1 偏 9.5°"之类的结论，都只在一个朝向区间上成立**（旋转扫描证明它是随朝向变化的，
不是常数偏置）。想继续调算法，先补一份**覆盖全朝向**的真机语料——这比换算法收益大得多。

### 待验证（需要用户配合）

> 在游戏里**按住 W 直着往前走**时，角色朝向 ≈ 镜头朝向，

问题只在"小箭头比较难测"。


## 真机"直走"对照实验（2026-11-23，蒙德）

方法：让角色**按住 W 直线行走**，此时角色朝向 ≈ 镜头朝向，于是
**青色箭头应当与白色视野扇形重合** —— 这就给了一条不依赖人工标注的真值链。

### 用视锥当参照，先剔掉"正在转镜头"的帧

录 35 秒（353 帧）。按"视锥在 ±5 帧内波动 < 5°"筛出**镜头稳定**的 283 帧：

| 通道 | 有效帧 | 与视锥差 <15° |
|---|---|---|
| v1 三点 | 104 | **104（100%）** |
| v3 主轴 | 179 | **179（100%）** |

镜头稳定时箭头中位 309.8°、视锥中位 308.6° —— **互差 1.2°**。

结论：**真机在稳态下是准的**。之前"30% 的帧偏 90~120°"的观感，
来自把"转镜头"也当成了误差（小地图随镜头转，箭头在屏幕上的角度本来就会变）。

### 但两条通道确实各自会偶发翻错

镜头一动就能看出来是谁翻的：

```
第136帧: 视锥 82° (3帧前 306°)   ← 视锥翻了 136°
         箭头 308° (3帧前 308°)   ← 箭头没动
```

29 个"视锥在动"的帧里，箭头**同向转动只有 5 个** —— 说明那次是**视锥**翻错。
反过来在另外几段是箭头翻错。两条通道的翻转**不同时发生**，这是好事：
以后可以做交叉校验。

### 已落地：收紧单帧跳变门限

10 fps 采样下，物理上限是 540°/s × 0.1s = **54°/帧**（ω 本身钳在 540）。
原版的门限是 130°，意味着 **90~120° 的假跳变会直接放过去**（真机每 40 秒能见到十几次）。

改动：
- `AbFilter` 增加 `flip_gate` 字段（默认仍 130，保证和原版逐帧对拍不变）
- 门限改为 `min(flip_gate, 540·dt·1.3, 且不低于 60°)` —— 按物理上限自适应
- 管线（gifa-demo）里把它设成 **65°**（= 10fps 物理上限 54° ×1.2；对应 `apps/gifa-demo/src/main.rs` 的 `AbFilter::with_gate(65.0)`）
- 新增测试 `tight_gate_rejects_impossible_jump`：120°/帧 必须被拦、50°/帧 必须跟上


## 交叉校验：用视野扇形否掉"持续错"的箭头

真机实测发现两条通道**从不同时翻**（某段是视锥翻 136° 而箭头没动，另几段反之）。
这就是一个天然的互证机制。

原来的逻辑有一个洞：

```rust
let confirmed = vote_new > vote_old || (self.suspect >= 2 && conf >= 0.5);
```

"连续 2 帧 + 置信度 0.5 就认" —— 于是一个**持续错**的观测量（比如把别的青色块
当成箭头）连错两帧就会被采纳，而扇形明明一直指着旧值。

改成：

```rust
let cone_vetoes = cone_conf > 0.3 && vote_old > vote_new;
let confirmed = if cone_vetoes { false } else { ...原逻辑... };
```

**为什么不会误杀真实转身**：这个分支只在"单帧跳变 > 门限"时进入，
而一次转身受 540°/s 限制，10fps 下每帧 ≤54°，根本进不来。

### 离线回放（400 帧真机录制）

```
门限  与视锥差 >90° 的帧   帧间 >90° 跳变
130°（原版）   93 → 46            50 → 2
 65°（现在）   93 → 36            50 → 7
```

- "与视锥差 >90°"是**准不准**的指标：65° 门限把它压到 36（原版 46）
- "帧间跳变"是**稳不稳**的指标：原版更平滑，代价是它会把持续错的观测也吃进去

两个指标此消彼长，取 65° 是因为准不准更重要（跳变还有 α-β 平滑兜着）。
而且 65° 恰好是物理上限的 1.2 倍，有依据。

### 配套

- `AbFilter::with_gate(deg)` —— 外部构造带门限的滤波器（私有字段用不了结构体更新语法）
- 测试 `cone_veto_blocks_persistently_wrong_arrow`：扇形否掉时连续 4 帧都不采纳；
  扇形也翻过去之后才允许改判
- `examples/filter-replay` 可以把任意录制目录回放进来对比指标


## 视锥通道：白膜几何校验（2026-11-23）

### 先说一个不成立的方案

"用箭头否决视锥跳变" —— **不成立**。

相机转身时：箭头不动、视锥大幅移动。这跟"视锥翻错"的画面**一模一样**，
两者无法区分。所以这条不能做，做了会把真实转身全部误杀。

### 改成：验证"扇形内部确实是白膜"

峰配对只保证"某个角度有一条上升边、45° 外有一条下降边"，
两块互不相关的白色图标也能凑出这样一对（真机观测到过一次 136° 翻转）。
但**扇形是一整片半透明白膜**：它覆盖的极坐标格应当整体比正对面（+180°）
同半径的格更白。

实现用已经累好的 `sr/sg/sb/cnt`（不额外扫像素）：比对 ±30°、12 层里第 3~9 层
共 100+ 格，要求**过半格"内部比对面亮 ≥2"**，否则把 conf 打 3.5 折。

### 实测

| 语料 | 帧数 | 校验未过 | 未过的帧与箭头差 |
|---|---|---|---|
| 真机 400 帧 | 400 | 51（13%） | **61.2°**（过的帧 27.9°） |
| 视频 150 帧 | 150 | 2 | —（这两帧本来也判无效） |

真机上"未过白膜校验"的帧，与箭头的分歧是过关帧的 **2.2 倍** —— 说明它抓的是真问题。
视频语料只误伤 2 帧，不影响那条 138/138 的路径。

配套：`ConeResult.membrane_ok` 暴露出来（诊断 + 门控），
测试 `membrane_check_distinguishes_real_sector`（真扇形过、中间挖空不过）。


## 两个被数据否掉的改进（2026-11-23）

### A. v3 用青色强度加权做 PCA —— **变差，已撤回**

想法：小箭头只有 ~28px，阈值附近的像素会让二值质心挪半个像素。
用 `min(g,b) − r` 的强度当权重，理论上等价于亚像素加权。

实测（同一份语料）：

| 语料 | v3 二值（原） | v3 强度加权 |
|---|---|---|
| 真机 39 帧 | 中位 **2.4°**，p90 6.3° | 中位 3.0°，p90 6.5° |
| 视频 138 帧 | 中位 **4.0°**，p90 8.6° | 中位 4.8°，p90 8.7° |

两份都变差。原因大概是：青色分数在箭头内部接近饱和，加权后主轴被"最亮的那一小块"
（鼻尖附近）拉偏，反而不如"所有超阈值像素等权"。

### B. 放宽 v1 的三点几何门 —— **只会放进垃圾，已停手**

先把三道硬门参数化（`nose_far_ratio` / `nose_flat_min` / `tail_angle_min|max`，
默认值与原版一致，对拍不受影响），再在真机帧上扫：

| 参数 | v1 覆盖 | 与 v3 一致（<15°） |
|---|---|---|
| 原版门（95..162 / far 1.02 / flat −0.5） + margin 4 | 93 | 3% |
| 放宽角度到 80..175 | 93 | 3% |
| 放宽 far 到 1.25 | 103 | 6% |
| 放宽 flat 到 −1.0 | 93 | 3% |
| 三者都放宽 | 103 | 6% |

再看另一组：把 `bisErr` 从 25 收回原版 15、`angMargin` 从 18 放到 4：

- 视频语料 138 帧 → 98% 一致（中位 4.0°）✅
- 真机 `target/walk` → 只剩 **3 帧**有效（bis=15 太严）
- 真机 `target/live` → 93 帧，但只有 **3%** 与 v3 一致

结论：**v1 在真机上的低覆盖率不是"门太严"造成的，而是小箭头的几何本来就不满足那套
三点评分**；放宽只会把错答案放进来。现有 25/18 这一组已经是"覆盖 × 正确"的拐点。

### 这轮得到的参数化（保留）

`ArrowParams` 多了 `nose_far_ratio` / `nose_flat_min` / `tail_angle_min` /
`tail_angle_max`，默认值与原版完全一致 —— 以后要按设备/画质调门，不用再改硬编码。
配套 `examples/gate-sweep` 可以在任意帧目录上扫参数、看覆盖率与一致性。


## 两路融合实验 → 结论：按箭头绝对尺寸裁决（2026-11-23）

### 尝试过的融合规则（都被数据否掉）

1. **加权平均**（v1 更精确 → 权重 0.5~0.85）：
   视频语料从 0.03° 变差到 0.7° —— v3 的 4° 误差把 v1 稀释了。
2. **固定信任 v1**：
   真机语料 28 帧 v1 全开 → 中位 8.3°（v1 在真机上是 9.3°，v3 只有 2.4°）。

关键发现：**v1 和 v3 的优劣按"域"反转**，不是固定关系：

| 域 | 箭头像素 | v1 | v3 |
|---|---|---|---|
| 视频（放大镜） | ~60px | **0.03°** | 4.0° |
| 真机（原版） | ~28px | 9.3° | **2.4°** |

所以"谁当主通道"只能按**箭头的绝对像素尺寸**裁决，而不是谁都有理。

### 落地：`fuse_arrow`

```
箭头轴长 ≥ 40px → 信 v1（三点拟合在放大箭头上近乎完美）
箭头轴长 < 40px → 信 v3（PCA 对尺寸不敏感，小箭头上更稳）
两路差 >20°     → 标 suspect，滤波层把置信度 ×0.4（宁可保守）
```

`detect-eval` 实测：

| 语料 | 结果 |
|---|---|
| 真机 39 帧 | 39/39 走 v3，中位 **2.4°**，最大 9.7°，翻转 0 |
| 视频 138 帧 | 138/138 走 v1，中位 **0.0°**，最大 2.3° |

同时修了一个连带问题：原来的箭头窗口**无条件裁切 55%**，会把已经裁过的帧
（真机语料 126px、箭头占大半）再裁一刀，v1 覆盖率 28/39 → 0/39。
改成"全窗先跑，只有被 `p99<100` 闸挡掉才裁切"。

### 配套

- `detect.rs::fuse_arrow`（纯函数，可单测）+ `ArrowPick`
- 测试 `fuse_arrow_routes_by_size`（大箭头→v1、小箭头→v3、分歧→suspect）
- `suspect` 接入 gifa-demo：suspect 帧的 α-β 置信度 ×0.4
- `examples/detect-eval`：跑 detect_window（含裁决）在语料上的精度，按来源分桶


## 第一份全朝向真机语料（2026-11-23，蒙德雪地）

用户按 `docs/CORPUS.md` 录了一段原地转 360° 的素材，抽 57 帧人工标注。
**这是第一次有覆盖全部 8 个 45° 桶的真机真值**（老语料 28/39 帧挤在 315°~360°）。

存档：`docs/calibration/m1-labels.json` + `docs/calibration/m1-sub/`（57 帧，5.6MB）

### 结论一：v1 的「9° 系统偏差」被推翻

老语料上 v1 是 9.3°，看着像常数偏置。新语料分桶看带符号误差：

| 朝向桶 | v1 均值 ± 标准差（帧数） |
|---|---|
| 45°~90° | −120.9° ± 2.9° (2) ← 两帧全是翻转 |
| 225°~270° | +2.6° ± 2.6° (12) |
| 270°~315° | −3.1° ± 2.9° (3) |
| 315°~360° | −4.4° ± 3.1° (3) |

有效帧里 v1 是 **±4° 以内**，没有常数偏置。老语料那 9.3° 是**那个会话/那种外观特有**的，
不能推广。**所以"给 v1 定标减 9°"这件事不能做** —— 会把新样本上的好帧反而弄坏。

### 结论二：v3 在真机上偶发 ~120° 大错（8.8%）

| 算法 | 覆盖 | 中位 | p90 | 最大 | >45° |
|---|---|---|---|---|---|
| v1 | 20/57 | 4.8° | 117.9° | 123.8° | 2 |
| **v3** | **57/57** | **2.0°** | 25.5° | 147.5° | **5** |
| 管线 | 57/57 | 2.0° | 25.5° | 147.5° | 5 |

5 个坏帧的误差是 −120°、−121°、−121°、−130°、+147.5°（不是 ±180° 翻转）。

逐帧看图后定位到原因：**小地图上的红白导航路线条从箭头中间横穿过去，把箭头尖端整个盖掉了**。
剩下的后半截楔子本身是个"小三角"，PCA 主轴于是偏了 50~60°，方向就差 120°。

试过但**无效**的两个修法：

| 修法 | 结果 |
|---|---|
| 中心圆内取所有青色像素的并集（让碎块合起来） | 更差：16 帧 >45°（圆里混进别的青色） |
| 闭运算补缝（r=2） | 更差：7 帧 >45°（缺口比结构元大得多，补不上） |

### 结论三：用「尖端钝度」识别被切断的帧

真正能用的信号是形状学指标：

```
tip_blunt = 最外侧 10% 的宽度 / 中段(30%~70%)宽度
```

正常箭头一端尖、一端燕尾，两端都不超过中段宽度（实测 52 个好帧 **最大 0.82**）；
被切断的残片会露出一个比中段还宽的平截面（4 个坏帧 **0.89 / 1.16 / 1.16 / 1.16**）。

| 阈值 | 拦下坏帧 | 误伤好帧 |
|---|---|---|
| 0.80 | 4/5 | 1/52 |
| **0.85** | **4/5** | **0/52** |
| ≥0.90 | 3/5 | 0/52 |

取 **0.85**。落地方式不是硬丢弃，而是**把置信度压到 0.2 并标 suspect**：
滤波层"连续 2 帧 + conf≥0.5"的确认路径于是走不通 —— 宁可保持上一帧，
也不要把 120° 的错值认下来（`low_conf_never_confirms_persistent_wrong_value` 覆盖这条）。

剩 1 帧（seq 305，+147.5°）钝度只有 0.32，不是被切断，是定符号错了，暂未解决。

### 结论四：40px 主通道阈值没被这批数据考验到

这批真机箭头轴长 **26.0~34.9px（中位 29.2）**，全部 <40 → 全部走 v3。
阈值离最大值只有 5px 余量，如果哪天改 HUD 缩放让箭头变大，阈值两侧的行为需要重新确认。


## 修掉「符号判错」那一帧：改 4 邻域连通（2026-11-23）

seq 305 是 57 帧里唯一**不是**被路线条切断、却偏 147.5° 的帧。

逐帧看图后定位：箭头右边有个**白色楔形**（带深色描边），楔形里还嵌着一小块**亮青色**。
它和箭头本体只**斜对角**擦着 —— 8 邻域连通会把两者并成一块，于是
"窄端定鼻尖"看到的最窄处在楔形里那块青色上，符号就选反了。

**改动**：`largest_blob` 从 8 邻域改成 **4 邻域**。箭头本体是实心块，4 邻域不会切碎它；
只靠斜对角相连的外来色块则会被分开。

| 语料 | 改前 | 改后 |
|---|---|---|
| 真机 57 帧（全朝向） | 中位 2.0°，>45° **5** 帧，最大 147.5° | 中位 2.0°，>45° **4** 帧，最大 127.8° |
| 真机 39 帧（老，单朝向） | 中位 2.4°，最大 9.7° | 中位 2.4°，最大 9.7°（不变）|
| 视频 138 帧 | 走 v1，0.0° | 走 v1，0.0°（不变）|

### 连带发现：钝度门控失效了，但视锥否决接住了

上一轮加的 `tip_blunt` 门控（阈值 0.85，拦下 4/5）**在 4 邻域下失去区分力**：
坏帧钝度变成 0.59/0.59/0.59/1.09，而好帧最大到了 1.35。所以**撤掉了它的门控作用**，
