## 实战抓到的 7 个问题

### 1. 独占全屏根本无法覆盖（没法修，只能要求）

游戏全屏时 `WindowFromPoint` 在我们自己的窗口坐标上返回**游戏窗口**：
独占全屏接管显示输出，置顶也没用，鼠标点击也不会传给别的窗口。

→ 产品要求：游戏必须用「窗口化」或「无边框窗口」。UI 里应给出这条提示（待做）。

### 2. 拖不动：`-webkit-app-region: drag`

原版 CSS 的标题栏写了 `-webkit-app-region: drag`（Electron 特性）。
**WebView2 没有宿主实现它，但 Blink 仍然吞掉该区域的鼠标事件** —— 页面收不到 mousedown。

→ 改成 `no-drag`，拖动由外壳驱动。

### 3. 第一次点击只激活、不派发事件

`WS_EX_NOACTIVATE` 的宿主窗里，WebView2 **不派发 DOM 鼠标事件**。
用户观察到的现象非常典型：*先点一下最小化（激活窗口），之后拖标题栏就正常了*。

→ 去掉 `NOACTIVATE`（允许激活），并在 `WM_ACTIVATE` 时若左键按着且光标在拖动区，
**立刻开始拖动**，做到"一次点击就能拖"。
代价：点浮窗会把焦点从游戏拿走（WebView2 的取舍，Electron 版没这问题）。

### 4. 拖动区坐标没换算

页面上报的拖动区是**窗口内**坐标，轮询拿到的光标是**屏幕**坐标，差一个窗口原点。
表现是"按下了但判定不在区域内"。

→ 加窗口原点偏移。

### 5. `RegisterHotKey` 自动重复

按住 `Alt+I` 时 Windows 连续发 `WM_HOTKEY`，实测 **8 秒内触发了 10 次**，
窗口在沉浸模式里反复横跳。

→ 同一动作 300ms 内只认一次（`RegisterHotKey` 拿不到 keyup，只能按时间；
钩子键仍用"按下集合"去重）。

### 6. 截屏截到的是"压在上面的窗口"

浮窗被盖住时 GDI 按屏幕坐标取像素，取到的是游戏画面 —— 识别于是把游戏里的青色
（原神的水、特效）当成小地图箭头，日志里出现过 `cyan=0.1517 arrow=321°` 这种假方位。

→ 每次采样前先判定"浮窗是不是真的露着"（`WindowFromPoint` 命中自己），
被盖住就**暂停识别并写日志**。宁可不报，也不要报一个看着有数据、其实是别人画面的方位。

### 7. 置顶会被游戏抢走

游戏会周期性把自己抬到最前。只在"发现自己不是 topmost"时重设不够
（自己标记是 topmost，但对方也是 topmost 且后抬起）。

→ 改成**无条件重新 `SetWindowPos(HWND_TOPMOST)`**，并且被遮挡时立刻抢回来。

## 已知限制（写进产品约束）

- 独占全屏不可覆盖 → 必须窗口化/无边框；
- 点浮窗会夺走游戏焦点（WebView2 行为）；
- GDI 截屏在独占全屏下返回黑帧；
- 手柄只在 XInput 上验证过，其它 API（DS4/DInput）未测；
- 识别仍是占位算法：本次视频里没有小地图，`cyan=0`，所以"识别真实小地图"这一项**没有验证**。

# 第二次真机联调（2026-11-22 下午）

## 新增能力

| 能力 | 说明 |
|---|---|
| `--game <秒>` | **直接采游戏窗口**（`UnityWndClass` 客户区），不再依赖视频页 |
| `--autocenter` | 自动定心：扫大面积青色块，逐个交给箭头检测器验收，反推圆心与半径 |
| `--list-windows` | 列出可见顶层窗口（类名/标题/尺寸），排查"找不到游戏窗口" |

## 实测（至冬 · 冰原）

```
[game] 窗口 hwnd=0x17E07C0 2560×1440 @(0,0)  小地图 ≈(222,168) 半径 245
[game] 叠加层已就位
[1] 抓到帧 148 帧（15s）     [2] 箭头有效 0/148（0%）
[3] 视锥有效 111/148（75%）  [6] 截帧 7.3ms / 检测 0.7ms
```

| 通道 | 结果 |
|---|---|
| 窗口挂接 / 叠加层 / 截屏 | ✅ 正常，7.3ms 一帧 |
| 视锥 | ⚠️ 63~100% 帧"有效"，但置信度只有 0.15，抽查的那帧角度偏 >100° |
| 箭头 | ❌ 0 有效；`analyze` 自己判 valid，角度偏 ~128°，被"鼻子在轴上（8°）"闸挡下（实测 13.7°）|

**结论：视觉在冰原上不work**。小地图底色是冰蓝，箭头是同色系的浅青，扇形与底图的对比也很弱 ——
和视频素材里冰原那段的结论一致。这段代码在**绿地**素材上是准的（144 帧人工真值，中位误差 0.03°）。

## 顺带修的一个真问题

真机帧里 `p99 < 100`（"这一帧没有小地图"的闸）把整帧否了：小地图直径 ~260px、
箭头只有 ~40px，用 253px 窗口时箭头占比 ~1%，p99 掉到 73。
现在**两个通道用两个窗口**：视锥用整窗（要看到扇形边缘），箭头用中心 55% 的裁切。

## 还差

* 真机在**绿地**（蒙德/璃月）复测 —— 这是目前唯一没验过的组合
* `--autocenter` 在视频上还没成功（候选块没过验收）；真机上待测


## 窗口位置与尺寸（2026-11-22 定稿）

**窗口压在小地图上 = 截自己。** 这是前两轮真机失败的真正原因之一：浮窗在左上角，
采样窗正好落在浮窗自己的像素上，于是"视锥 100% 有效、箭头 0 有效"。

| 项 | 值 |
|---|---|
| 默认位置 | **左下角**（工作区左+40、下-40） |
| 默认尺寸 | **720×450**（原 896×568） |
| 位置记忆 | 移动/缩放后自动写回 `settings.json`，启动原样恢复 |
| 启动期保护 | 启动后 2 秒内的 bounds 变化是程序自己摆的，不记 |
| 恢复时不 clamp | 用户故意让底边压到任务栏也不纠正（否则每次启动往上漂 85px） |
| 手动指定 | `--pos x,y` / `--size 720x450` |

验证：连开三次，位置稳定在 `(40, 900) 720×450`，不再漂。

真机复测时用：`gifa-demo.exe --game 20 --autocenter`（`--game` 会把浮窗整个隐藏）。


## 第三次：绿地真机复测（2026-11-22 16:00）

窗口已改左下角 + 720×450，`--game` 会隐藏浮窗，所以"截自己"这条路排除了。

### 参数扫描（每档 7~10 秒）

| ROI 半径 | 采样窗 | 箭头有效 | 视锥有效 |
|---|---|---|---|
| 0.030 | 95px | 0% | 100% |
| 0.040 | 127px | 10% | 100% |
| 0.050 | 159px | 1% ~ 38%（两次差异很大） | 100% |
| 0.065 | 206px | 0% | 100% |
| 0.080 | 254px | 3% | 97% |

自动定心给出 `cx=0.0861 cy=0.1149`（与手工量的一致），但半径估小了（0.02）。

### 关键结论：**原版算法也认不出真机的箭头**

把真机 dump 的 40 帧直接喂给参考实现（`harness.js analyze`，与原版逐字一致）：

```
40 帧，判有效 0 帧（0%）
```

也就是说这不是移植问题。离线看单帧的门限：

```
cyans=373  corners=[67.3°(r14.6,span3) 229.6°(16.3,3) 286.8°(14.2,span22) 323.4°(22.1,4)]
GATE noChosen —— 所有三点组合都被硬约束否掉
```

真实箭头指向正北（图上很清楚），但右翼的半径 22.1 比左翼 16.3 大了 36% ——
**旁边的青色图标并进了同一个连通块**，于是"两翼对称"的前提不成立，
`o≥95°`/`bisErr≤15°` 全过不了。提阈值（112→190）也不解决：cyans 只从 373 掉到 333。
