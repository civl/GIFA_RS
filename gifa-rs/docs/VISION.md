# 视觉识别：骨架（M8a 的先行版）

更新时间：2026-11-22。**这不是 M8 的交付**，是把"截帧 → 采样 → 出角度 → 叠加层"这条链路
先接通的骨架。真正的算法移植（M8b）仍然没做，黄金帧基线也还没有。

## 链路

```
采样窗（屏幕坐标）
      │  GDI BitBlt，只截这一小块
      ▼
   Frame(RGBA)  ──▶ detect_simple  ──▶ VisionEvent ──▶ overlay_update
   216×216 典型        占位算法            带耗时          红箭头 + 绿弧
```

采样窗由 UI 线程每帧算好放进 `Arc<Mutex<Option<SampleBox>>>`，识别线程自己取 ——
窗口移动、切布局、换分辨率都不需要重启线程。

## 为什么先用 GDI 而不是 DXGI

DXGI Desktop Duplication 是二期该走的路（性能、独占全屏），但它的 COM 生命周期、
桌面复制会话重建、全屏切换都要专门处理。骨架阶段的目标是"能拿到一帧"，
把 COM 调试和链路验证混在一起只会两边都慢。

GDI 走 DWM 合成后的桌面：窗口化/无边框游戏拿得到；**独占全屏会返回黑帧**——
那本来就要求用户改窗口化（见 `IMMERSION.md`）。

## 箭头通道：已按原版移植并对拍通过 ✅

`crates/gifa-vision/src/arrow.rs` 是对 `webview-preload.js:566-960` 的**逐步骤移植**：

```
自适应阈值(p99≥100, floor 112, ×0.74) → 半径带 mask → 连通块(取最大)
→ 72 格径向剖面 → 三点平滑 → 候选峰(≥50% 峰高、间隔≥25°) + 支撑宽度
→ 峰值精修(平均单位向量) → 枚举三点组合打分 → 定鼻尖
→ 角度 = 两尾翼中分线反向；validity 七道闸
```

**对拍结果：33 帧合成语料（箭头 + 视锥两条通道），Rust 与 JS 参考实现逐帧一致**
（最大角度差 0.0000°，最大 conf 差 1.11e-16；valid / cyans / tipFrac / angMargin /
radMargin / noseFlat 全部相等）。

### 对拍是怎么做的

`tools/vision-ref/harness.js` 在运行时**从原版源码里切出算法段**（不抄、不重写），
在 node 里跑；同一批 `.bin` 帧再喂给 Rust：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/vision-golden.ps1
```

合成帧生成器画的是"钝鼻 + 两个尖尾"的飞镖：鼻子半径 0.17、尾翼 0.235、
翼角 ±130°（两尾翼夹角 100°）。这些比例是按原版注释里的实测值（tails 100°、
nose→tail 123~137°、nose 半径最小）反推的 —— 画成实心三角会直接判无效。

### 移植时踩的四个坑

1. **角度空间**：原版给的是 `atan2` 角（0=东、逆时针），叠加层要罗盘角。
   换算是 `compass = (90 − atan2) mod 360`，**不是** `+90` —— 写成 `+90` 会让所有方向镜像。
2. **诊断字段是舍入过的**：原版返回 `Math.round(x*100)/100`，而 Rust 的 `round()`
   在 .5 上朝远离零舍入，JS 是 `floor(x+0.5)`，差 0.01。
3. **阈值比较要用 double**：`score < thr` 里 thr 是小数，我第一版截断成整数，
   卡在阈值上的像素会多算进来。
4. **f32 缓冲的取整位置**：JS 用 double 算完再存进 `Float32Array`（只取整一次），
   Rust 若全程 f32 运算会提前取整，边界像素归属分歧。

## 视锥通道：已按原版移植并对拍通过 ✅

`crates/gifa-vision/src/cone.rs` 移植 `analyzeCone()`（`webview-preload.js:1008-1358`）：

```
极坐标格(120×12) → 不透明白核剔除 + 膨胀 → 每格 RGB 累加
→ 逐角度找「半径边」：两侧各 2 格取均值，三通道联合最小二乘解 α，
  且要求三通道解出同一个 α（水→陆这种底色边界残差超标，判 0 并投反对票）
→ 可见层严格多数（≥5 层）才算一条边
→ 配对：上升边 −45°、下降边 +45°（张角恒 90°），单边也允许
→ 亚格细化（±2 格强度质心）→ 中轴 → 角度
```

它认的是**半透明白膜** `dst = src + α·(255−src)`，α 随半径衰减（0.17R≈0.35 → 0.72R≈0.12）。
合成语料必须按这个混色画，画成实心白会解出 α≈1，被 `A_MAX=0.45` 直接否掉。

**对拍同样 33 帧全一致**：视锥最大角度差 0.0000°。
`--vision-synth` 端到端：视锥 **178.5°**（期望 180°，差的 1.5° 是算法自己的量化步长，
和原版一模一样）。

### 顺带修掉的三个坐标/尺寸坑（23 日）

1. **角度空间串了**：检测输出罗盘角，时序层内部用数学角。第一版把罗盘角直接喂进
   滤波器、出口又转一次 → 叠加层视角显示 270.58°（真实 179.42°）。现在进出都换算。

### 精度：干净图上 1.2°，有背景时 11°

把同一枚箭头贴到平底色上（净图）：输出 **90.2°**，对称轴真值 89.0° → **误差 1.2°**。
放回小地图背景：输出 **101.8°** → 误差 11°。

原因不在阈值（把系数从 0.74 调到 0.97，选中的像素数一模一样）：
小地图里另有一块青色（约 140~150°、半径 26）**混进了同一个连通块**，
角数从 4 涨到 5，配对选出的两翼被拉偏，轴就歪了。

### 形状模型重做：v2 凸包 + 凹口（`crates/gifa-vision/src/template.rs`）

先说结论：**"改形状模型"这条路，单靠改形状分不出方向**。

真机箭头近似等边（尖端 17.5 / 两翼 16.6·16.7 / 底边 12.6），三个顶点谁当尖、谁当翼，
光看形状没有信息量。实测把"参数化四边形 + IoU 拟合"跑上去，三种顶点分派 IoU 几乎一样高，
角度在 211° / 334° / 107° 之间乱跳 —— 不是调参能救的，是**问题本身欠定**。

真正能把方向钉死的只有一样东西：**凹口**。底边中点比两翼更靠近中心（12.6 < 16.6），
整块掩膜唯一的内凹点就在"背后"。所以 v2 的做法是：

```
最大青色连通块 → 边界点 → 凸包 → 离凸包最远的边界点 = 凹口
             → 方向 = 质心的反方向 → 对称轴 ±25° 精修
```

凹口深度 < 0.03·R 时直接返回 None（纯凸形状没有方向信息，宁可不报）。

v2 单独用的精度不如 v1（净图 99.8° vs 真值 89.0°，v1 是 90.2°），
但它的**错误方向和 v1 不一样** —— 这正是它的用处。

### 两模型互证（结论：暂时只能当诊断，不能当闸）

v1 给角度（干净帧上准），v2 当独立第二意见；两者差 **>16°** 就判这一帧形状被污染、不上报。

| 素材 | v1 | v2 | 差 | 处置 |
|---|---|---|---|---|
| 真机干净箭头 | 90.2° | 99.8° | 9.6° | 通过 |
| 真机箭头+地图背景 | 101.8° | 137.5° | **35.7°** | **挡掉** |

真实视频（蒙德 1080p / 30 秒）上的效果：

| 配置 | 有效帧 | >90° 跳变 |
|---|---|---|
| 只有 v1 | 247~278 | 1~3 次 |
| v1 + 鼻子闸 | 247~278 | 0~1 次 |
| v1 + 鼻子闸 + 两模型互证 | 247 | 0 次 |

但**在真实视频序列上 v2 不可靠**：290 帧里有 **215 帧（74%）**与 v1 分歧 >16°，

不参与判据 —— 等它在序列上稳了再启用。

（v2 在两张静态真机图上是好的：干净 9.6° 分歧、带背景 35.7° 分歧；
但静态图过关 ≠ 序列可靠，这轮就是被这一点教育了。）

### 试过但**不成立**的两条：帧间位移、视锥互证

**1. 帧间位移方向（相位相关）——信号太弱**

设想：小地图随角色移动而滚动，相邻帧做相位相关就能拿到位移方向，
作为"箭头认不出时"的补充观测。实测（蒙德素材，1400×788 沉浸，约 10 fps）：

| 基线 | 位移中位 | 相关峰值中位 | 方向一致性 |
|---|---|---|---|
| 1 帧 | 0 px | 0.91 | — |
| 5 帧 | 1 px | 0.38 | 27% |
| 10 帧 | 0~1 px | 0.32 | 45% |

三层原因，每一层都足以否掉这个方案：

* **尺度**：小地图约 100 m 铺 250 px → 0.4 px/m；角色 5 m/s → **2 px/s → 0.2 px/帧**，
  远低于可测精度；
* **静态件锚定**：外圈装饰和「北东南西」方位字不随地图移动，会把相关峰钉在 (0,0)；
  只取中心区域后峰值掉到 0.3~0.4，方向变成随机；
* **旋转**：这张小地图会随镜头旋转，纯平移的相位相关建模不了。

**2. 视锥互证——前提本身就是错的**

原以为"跑动时箭头（行进）与视锥（镜头）基本一致"，实测 55 帧里夹角中位 5.2°、p90 11.9°，
看起来可用。但接入后 290 帧里**误挡 16 帧**：

* 原神的移动是**镜头相对**的 —— 按 A/D 横移时箭头与镜头朝向**垂直**；
* 按 S 倒着走时两者差 **180°**。

放宽成"共线即可（0° 或 180°）"仍会挡掉横移帧。结论：这条不变量不存在，已撤除。

### 我们加的闸：鼻子必须在轴上

真箭头是轴对称图形，鼻子必然落在中轴上。实测这个量能把两类情况分开：

| 素材 | &#124;鼻子−轴&#124; | 角数 |
|---|---|---|
| 合成飞镖 ×30 帧 | 最大 **2.5°** | 3 |
| 真机干净箭头 | **6.5°** | 4 |
| 真机箭头+地图背景 | **13.9°** | 5 |

`arrow::axis_consistent()` 用 8° 卡这条线：挡住被污染的那一帧（它恰好就是偏 11° 的那帧），
不误杀前两类。**这是我们的增补，不在原版里**，所以 `analyze()` 的输出仍与原版逐位一致
（黄金对拍 33 帧 0.0000°），闸门只加在管线入口。

真实像素回归：`crates/gifa-vision/tests/real_arrow.rs` 用这两枚真机箭头钉住行为
（cyans 331 / 角数 4 与 5 / 角度 90.2 与 101.8，均与原版 JS 一致）。

### 标注约定（重要）

**从这个窗口的圆心，往青色箭头尖端拖一条线**。

* 工具自己把拖动向量换算成罗盘角（0=北、90=东……），不需要你心算角度

### 结果：算法在这段素材上几乎是精确的

| 指标 | 数值 |
|---|---|
| 可评估帧 | 138（另 6 帧人工判"看不出/没有箭头"） |
| 误差中位 | **0.03°** |

### 闸门阈值有数据支撑了

`|鼻子−轴|` 在这 138 帧上的分布：**中位 2.7°、p90 4.2°、最大 5.4°**。

| 阈值 | 会误杀的帧 |
|---|---|
| 4° | 15 帧 ❌ |
| 6° | 0 帧 |
| **8°（当前）** | **0 帧** |
| 12° | 0 帧 |

所以 8° 是"零误杀 + 留 2.6° 跨视频余量"的位置；被污染的那张截图（13.9°）仍会被挡住。
**阈值不用改，但它现在有了实测依据，不再是我拍的。**

### 视锥通道也顺手验了

138 帧里同时有视锥：与箭头的共线偏差中位 **2.1°**，74% 的帧在 20° 以内，0 帧反相 ——
说明扇形通道本身也是准的。剩下 26% 差 20~160°，是"镜头朝向 ≠ 行进方向"
（按 A/D 横移、边走边转视角），这正好印证了"视锥互证不成立"那条结论。

### 与之前"偏 11°"的关系

之前那张实机截图上算法偏 11°，在这段视频的 144 帧里**一次都没复现**。
说明那次是个例（那张截图的箭头局部被地图上的青色连通块粘住了），
不是普遍现象 —— 也解释了为什么 v2 互证在序列上会误杀 74%。

## 占位检测器做了什么

只做两件事，够验证链路：

1. **箭头**：采样窗中心圆盘带内（`RADIUS_MIN..MAX`）的青色像素（`cyan_score ≥ 112`）
   质心方向 → 罗盘角。
2. **视角**：近白像素（`min(r,g,b) > 200` 且 `max-min < 28`）质心方向。

**小地图存在性门控**照抄了原版：`cyan_frac < 0.0015` 就直接返回空——
没有小地图的帧（转场、对话、看视频）不能靠白像素硬凑一个视角出来。

⚠️ 明确不做的：自适应阈值（p99）、最大连通块、72 格径向剖面、三点枚举评分、极坐标格、
最小二乘白膜边、α-β 滤波、大跳门限、扇形投票。这些必须逐函数对照
`webview-preload.js:365-2050` 移植，凭理解先写一版会把对拍基线搞乱。

## 这轮修掉的 bug

**GDI use-after-free**：`BitBlt` 之后先 `DeleteObject(bmp)` 再读 `bits` ——
DIB 的像素内存归位图所有，删掉后读就是野指针。单元测试直接 `STATUS_ACCESS_VIOLATION`。
修法：**先拷贝像素，再清理 GDI 对象**。
